不要记忆 AI 名词：大模型时代问题空间的演化

1. 为什么我们总是在 AI 对话中”鸡同鸭讲”

面对 AI 领域的快速发展，我们经常会遇到一种沟通上的困惑：技术名词不断涌现，不同背景的人在讨论同一个话题时，很容易因为关注点不同，而产生理解错位。我在一篇文章里看到一个概念，叫问题空间和解空间，我觉得很适合用来解释这些对话。

举个例子，有人说，我最近在用deepseek写代码。旁边人问他，你为什么不用codex。他们俩的问题空间错位了。第一个人的问题空间是，他在使用什么模型，这时候的解可以是deepseek、claude、sonnet等等。第二个人的问题空间是，他在使用什么编程Agent，解可以是cursor、codex、智谱。

这时候还有一个人说，你为什么不用RAG，这又是另一个问题空间了，这个空间是有哪些AI相关的系统设计。RAG是一种思路，ReAct Agent是一种思路，Workflow也是一种思路。

所以我整理了一下大模型发展的问题空间，看看我们过去、现在、未来在用这些所谓的模型、矩阵，在解决什么问题，有哪些解决方法。这也许能帮助我们建立对一个领域的认知。

2. 计算机的发展史：一部不断抽象问题空间的历史

在这里其实想简单提一句，计算机的变迁也是一种问题空间演化。

最开始我们拥有了模拟电路，拥有高低起伏的信号。

后来有人把问题空间升级了，我不在乎这些信号到底是0.1还是0.2了，把信号转化为阶梯变化的数字信号，用0101表示文字、操作、指令。

再然后，有人抽象出了数据传输链路，抽象出了存储器，抽象出了cpu这种计算单元，开始利用0101做自动化计算。

然后我们为了充分利用cpu这一基础元件的性能，提取出了操作系统，终于屏蔽了底层电路的所有细节。接着程序员们开始利用操作系统的基础接口，使用高级程序语言编写各种应用程序。

计算机的发展史，本质上就是一部不断”抽象”的历史；而每一次抽象，都是因为人类把问题空间提升了一层。

3. x -> y：模型问题空间的起点

其实大模型的发展史也是一种问题空间演化，也是层层抽象的过程。

最开始，人们面对的问题是如何让计算机的输入对应到正确的输出。

我们在这里稍微往数学上抽象一点，这其实就是一个数学的集合论问题，已知x和y，求x到y的映射。

由于计算机只能识别数字，人们逐渐发现矩阵计算非常适合计算机。这个问题就逐渐演变成了，已知x，求一个矩阵w，让x映射到y,也就是我们熟悉的线性模型：$y = Wx + b$

从今天回头看，这只是一个非常简单的模型，但它第一次固定了模型求解的问题形式，就是如何求一组最优参数W，达到最佳映射。这里的W就是模型，求解过程就是所谓的模型训练过程。

从此以后，无论是神经网络、Transformer，还是今天的大语言模型，其实都沿着这个问题空间不断向前发展。

4. 模型问题空间的持续扩展

现在我们已经将问题空间转化为求矩阵W了。随着这个矩阵的复杂度逐渐变高，人们用它来解决的问题也在逐渐变化，也就是问题空间的变迁。

模式识别：机器如何找到输入中的规律？

最开始解决的问题叫做模式识别，这个阶段的问题是：如何让机器识别输入中的规律？

例如：给机器一张图片，它能不能判断这是猫还是狗？给机器一段声音，它能不能判断说的是哪个词？

这时候的解空间，也就是能选用的模型比较简单，比如K近邻法，根据输入特征，选取最近的K个点取平均值，离猫近它就是猫，离狗近就是狗。还有支持向量法，贝叶斯分类器。

特征工程：如何让输入更适合模型？

慢慢的，人们发现，特征输入会影响模型判断。人们开始对特征做处理，这时候模型没变，但人们的问题空间变了，开始变成怎么让输入变得更合适。插一句，我觉得这跟我们现在面对的大模型问题有点像，模型就是那个模型，我们每天也在可劲折腾，怎么让模型的输入更靠谱一点。

深度学习：能否让机器自动提取特征？

下一个阶段大家开始偷懒，觉得我也分不清哪个特征靠谱，哪个不靠谱，比如纬度跟人们的寿命长度关系，我哪知道它好不好。所以我不做判断了，都交给机器判断。也得益于算力的增长，这时候神经网络开始普及起来。这个时间段的问题空间就是，输入一些参数，让模型帮我去做分类，能解决的问题大概有分类、聚类。

随着算力的进一步加深，这时候问题空间没变，我还是要让模型认识猫猫狗狗，但我可以在原来的神经网络上不断堆叠层。原来神经网络可能只能提取表层特征，但随着层数堆叠，它也许可以提出去潜藏在一堆特征里的深层特征呢。这时候解空间就变成了深度学习。我理解它其实是神经网络的堆叠和变化。

深度学习里发展出了很多不同变种，可以在网上找图片看看，矩阵各种嵌套，当时解决记忆问题是通过隐藏状态（hidden state）的循环传递，让网络能够利用之前的信息。

大模型：从解决任务到涌现能力

再往后算力大发展，就来到大模型了。我感觉大模型多少有点先做出来，再总结规律的意思。这时候它的层数已经很深了，人们不再纠结它到底提取出了什么特征，反而卯足了劲想办法让它并行计算、快速输出，然后从模型的表现上总结规律。这时候人们发现，大模型居然神奇地能跟人类对话，表现良好。所谓的幻觉、循环也是在这个阶段出现的词汇，用来描述大模型的表现。

5. 大模型时代问题空间如何变迁

大模型成为基础设施后，后面就走上了计算机一样的路了。人们不再关注模型的细节，反而把大模型当作一个传感器，或者一个神奇的函数，给函数套上各种各样的系统，实现不同目标。这跟计算机有点像，现在也没人会去研究电子电路了，我们直接在它的抽象上解决问题就好。

如何让大模型持续对话
对话型大模型是最早出现的。大模型全程是大语言模型，它是语言模型的一种。人们天然就会问，它能不能对话？这成为了最早的问题空间。这里的解空间也很有限，人们给LLM加上了记忆，其实只是把历史聊天记录全部重新传一遍。

大模型如何处理图像和声音
我感觉多模态其实也可以放在这个阶段。模型还是那个模型，解空间不变，但是为了解决不同的问题，比如图像、声音，人们在LLM前后加了一个转换层。核心问题不变，问题空间横向拓展了，从聊天拓展到图像、声音了。

大模型可不可以完成一个固定目标？
接下来问题空间出现演变。大家觉得大模型既然这么智能，能不能让它完成一个固定目标呢？这出现了Agent。给大模型设置好固定的参数，它就可以做固定的事。早期有很多拟人Agent。比如简历润色大师呀，小红书爆款生成器呀。
后面Agent发展，添加上了很多工具，tool呀，mcp呀，也还是，核心问题没有变化，问题空间横向拓展了。

怎么让大模型在我的目标上表现更好？
大模型用上了，接下来就是优化。问题空间这时候收缩到了”我该如何使用大模型，让它表现更好”。Prompt工程是这时候出现的，Agent的各种范式，比如ReAct、Recursive都是这个时候出现的解决方法。这里插播一下，大家看这些资料不要看网上那些短视频，直接去吴恩达的网站上找，他们讲解概念非常准确。我看百炼的说明有时候都是直接从那抄的。

我该如何管理多个不同目标的大模型？
当Agent的功能已经被大家玩得很熟悉了，问题空间又进一步演化：我该如何管理多个大模型？Harness就是这个时间出现的概念。Harness好像还没有抽象得很好的范式，但是有很多我们已经在使用的工具。我们说的小龙虾也好，hermes也好，都是在这个层面。它集合了模型管理，工具、mcp、skill管理，prompt管理（soul.md），Agent管理。

我该如何让我的大模型工程化，让它可靠落地？
上面的小龙虾也好harness也好，大家都玩过，只能当玩具，不能大规模应用到生产。假如给你一个工具，跟你说它有80%可能性可靠，你也不敢把它丢到生产去玩。所以人们开始研究怎么让它可靠落地。
上下文工程控制准确输入，agent评估观察模型表现，计算模型的延迟、成本、安全性，意图识别解决用户交互，这都是工程化阶段出现的解法。我们做的很多事其实就在这一层面，只是对它的展开。

6. 如何定位 AI 项目的问题空间：从理论回到实践

面对层出不穷的新概念，其实好像也没什么好怕的，可以回到这个路径上来看看它对应哪个层级。

之前我用hermess调用小伙伴的智能问数，我在hermess上控制调用的安全性，控制上下文输入，然后小伙伴的智能问数解决查询数据库的安全性。这是在工程落地层。

之前hongbin分享的小模型微调，问题空间跟最初的机器学习类似，不确定特征，在几个固定答案中选出一个最佳答案。这是在模型选择层。
我们制作各种Agent时的意图识别，也跟这个问题相关，答案有限。我感觉，这也是我们能用小模型去优化它的速度的原因。这本来就是一个历史悠久的领域。

我们做的日志查询工具，配置了一些固定的工具、预设的prompt，然后Agent设定好了范式。我感觉它像是harness层，只是治理，没有强约束，它归根结底还是一个需要人类二次校验的不可靠工具。一个99%准确度的工具，我们自己用得热火朝天，出了错纠正就好，但这种工具不能拿到生产给用户使用。

7. 问题空间收敛：从 AI 系统设计到代码实现

回到AI应用开发，我们这时候已经确定我们的目标是让它可靠落地了，也通过系统设计解决了功能、安全性、评估等问题，这时候问题空间就退化成了写什么样的代码达成目标。

这里要解决几个问题，模型调用，组合成Agent，上下文管理，tool call，skill管理。不同 AI 框架，本质上是在这些问题空间中提供不同层次的抽象。

例如，阿里的 DashScope 更偏底层能力，主要提供模型调用能力，其他部分如 Agent 编排、上下文管理、工具调用等都需要开发者自行实现，因此自由度高，但开发成本也更高。

常见的 LangChain 则进一步提供了一层应用抽象，将模型调用、Agent 组合、上下文管理等能力进行了封装。但当应用复杂度提升，需要更精细地控制 Agent 执行流程时，就会进入 LangGraph 这样的流程编排框架。

LangGraph 可以通过图结构描述模型和工具之间的调用关系，更方便地实现 ReAct Agent 等复杂流程。

同时，LangChain 生态还提供了 LangSmith，用于观察和评估模型表现。不过它更多是将评估能力工具化，实际使用中仍有一定限制。

离开Python生态，回到 Java 生态，Spring AI 提供了比较方便的 Tool 配置能力，但在 Agent 范式支持上相对有限；AgentScope 则预置了一些 Agent 模式，可以直接调用，但在 Tool Call 等细节上仍需要开发者进行额外实现。插一句话，我感觉Java的包追求完整与稳定，倾向于把多个能力封装在一个框架里，这种大而全的包反而会增加入门学习者的理解成本。这时候可以先回到Python，直接使用Jupyter Notebook 写一些小 Demo，快速验证想法。通过实际调用不同的包，理解模型调用、Agent 编排、上下文管理、Tool Call 等不同层级分别解决什么问题，之后再回到Java，会更容易建立整体认知。

AI 领域之所以让人感觉混乱，是因为它正在经历类似计算机早期的发展阶段：底层能力刚刚成熟，上层抽象还在快速形成。大量新工具并不是互相竞争，而是在不同抽象层解决不同问题。

所以我们接触新东西的时候，不要记忆 AI 名词，要定位 AI 名词。技术会变化，工具会迭代，但它们试图解决的问题，往往具有稳定的规律。
